# 反馈三阶段与简化问题传递实施计划

日期：2026-11-04。起点：`4aa8730`（11.4 精简反馈Prompt与输出协议）。

## 目标与范围

每个反馈 Agent 的执行过程分为三个阶段：核对并确定问题、生成本阶段操作、复核并输出。阶段内保留短步骤。整个程序仍依次执行 Add → Replace → Remove。

当前任务按单个源句抽取事实，删除跨句推断和多句证据拼接的提示。源句编号字段继续使用数组，模型生成的新事实只填写一个有效编号。历史数据中相同事实合并后的多个来源编号保留，不把旧记录强行截成一个编号。

模型只输出本阶段操作与简短 handoff；取消 handoff_results，不恢复 issues、reviewed_* 或模型评分。三元组分数继续由程序填入 0.8。

## 第一步：重排三个反馈 Prompt

| Agent | 阶段一：核对并确定问题 | 阶段二：生成本阶段操作 | 阶段三：复核并输出 |
| --- | --- | --- | --- |
| Add | 根据单句找关系，对照当前集合、差异和收到的问题 | 完全遗漏才新增；已有错误、嵌套未拆交给 Replace | 核对依据、词形与重复，输出 add、handoff |
| Replace | 检查主体、动作、对象、限定和内部关系 | 一条修正为一条或多条；内部关系已有正确独立表达时保留现有条目 | 检查完整集合的事实保留、字段边界与重复，输出 replace、handoff |
| Remove | 对照源句判断完整重复、部分重叠和不同事实 | 完整重复才删除，明确 keep_index；部分重叠交给 Replace | 确认独有内容保留且 keep_index 未删除，输出 remove、handoff |

修改 feedback_add、feedback_replace、feedback_remove 的 TASK_PROMPT。共享表达规则保留词形、必要限定、背景省略和证据要求。原有不同判断场景的短示例保留；不增加跨句示例。

## 第二步：收紧新事实的单句依据

1. feedback_common：每个新增或替换结果依据一个源句，evidence 是该句中的连续原文片段。
2. relationship_extraction：删除跨句说明；新抽取条目校验单句编号和本句证据。兼容现有精确来源恢复，但恢复结果有歧义时记录拒绝，避免任取一个编号。
3. entity_extraction、triple_splitting、text_comparison：删除暗示跨句补全的指导，明确按对应源句检查；保留同句内部的指代、嵌套、目的与风险关系。
4. feedback_operations：新三元组必须只有一个有效 source_sentence_id，证据必须位于该句。handoff 是定位问题的提示，可关联多个待比较条目与来源，不用于拼接新事实。
5. 旧文件不改写；保留旧记录的来源和审计。格式校验不声称能判断语义正确性。

## 第三步：删除模型的状态回执

模型输出：

```json
{"add": [], "handoff": []}
```

Replace、Remove 分别将 add 换成本阶段操作键。每项 handoff 只含 target、source_sentence_ids、indices、problem。

模型收到的 handoff 只含 source_sentence_ids、indices、problem。由调度程序选择目标阶段，内部 id、历史编号、投递状态均留在审计中。有无收到问题都使用相同固定 Prompt；核对收到的问题纳入阶段一。

操作中的 reason 解释修改依据。模型不输出问题已解决或尚未解决的状态。

## 第四步：更新程序调度与审计

1. 阶段开始时选取交给该阶段、尚未成功投递的问题，映射为当前编号。
2. 调用模型并校验本阶段操作与 handoff；执行有效操作，保留既有失败回退策略。
3. 程序记录投递到哪个阶段及该次执行状态。阶段有效执行（包含无操作回复）记录 delivered；调用、整体校验或操作批次失败记录 delivery_failed，供有限返修使用。delivered 仅表示完成该次阶段调用，不表示语义问题已解决。
4. 新转交问题由程序生成内部 id，保存来源与原始定位；每步修改后更新所有问题的当前编号。
5. 首轮 Add → Replace → Remove 后，仅对仍未投递的 Add/Replace 问题安排最多一轮返修；必要时 Add → Replace → Remove，否则 Replace → Remove。返修后仍未投递的问题保留记录，不再循环。
6. 已投递的问题不因缺少回执再次触发返修。后续 Agent 仍可独立发现问题并生成新的 handoff。
7. 审计使用 handoff_log（完整记录）、undelivered_issues（目标 Agent 尚未成功接收）、review_issues（重建、对比或人工核查提示）和 unverified_issues（语义状态未经验证）。移除旧 unresolved_issues 的“模型判定已解决”语义。
8. 阶段快照、实际 System/User、原始回复、接受与拒绝的操作、有限返修记录继续保存。协议版本更新为 task_outputs_v3。

## 第五步：更新导出文档与维护说明

更新 export_feedback_prompts.py，删除旧的 handoff_results 条件拼接说明。分别捕获空/非空 handoff 的真实调用，验证除业务数据外固定提示完全相同。更新受影响 Agent 的完整 Prompt MD、HTML、JSON、总览和反馈分步说明；核对源码行号与可点击链接。

## 第六步：验证与完成

- Add 转交 Replace，Replace 无回执也可正常修改；Remove 获得更新后的编号。
- 已投递问题不会反复触发返修，循环转交最多执行一轮返修。
- 无操作回复只表示该阶段没有提出修改，不自动认定问题解决。
- 调用失败、解析失败、无效来源、替换批次失败均记录；输入事实按既有策略保留。
- 拒绝新事实使用多个源句、跨句拼接证据；合法单句事实正常接受。
- 旧来源记录及基线文件不被改写；固定分数、主流程和回放保持兼容。
- 全量离线测试；校验短示例可解析和执行；核对文档固定内容、变量、源码哈希、链接和行号。
- 代码与文档一起本地提交。未运行真实模型时明确说明，反馈质量仍需新运行结果评估。

## 实施结果

上述六步已完成。

- 三个反馈 Agent 已按三阶段重排；共享 Prompt 已删除状态回执说明。模型只输出本阶段操作与 handoff，内部编号与投递记录由程序管理。
- 新抽取、新增和替换结果按单句来源与连续原文证据校验；历史多来源条目保留。实体、拆分、对比的相关提示已同步调整。
- 调度与审计已更新为 task_outputs_v3，失败投递可进入最多一轮返修；已投递记录仍标为语义未经验证。
- 76 项离线测试通过，覆盖阶段衔接、编号映射、无回执、失败投递、有限返修、单句证据和历史来源保留。
- 16 个固定示例（Add 4、Replace 9、Remove 3）通过 JSON、协议和操作执行校验。
- 已重新导出 14 个 Agent 的 MD、HTML、JSON 及总览；核对 17 个来源文件哈希、81 处提示来源范围和 82 个源码行号链接。三个反馈文档的固定代码块与导出的消息内容逐字一致，空与非空 handoff 的实际调用捕获也通过核验。
- 尚未调用真实模型跑新一轮数据；以上验证确认程序与协议可执行，反馈质量及宽松匹配 P/R/F1 的变化需用新运行结果评估。
