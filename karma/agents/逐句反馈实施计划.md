# 逐句反馈实施计划

日期：2026-11-04。基于提交 d401c9c（11.4 简化prompt）。状态：已实施，94 项离线测试通过。后续要求已纳入：重建文本和对比也默认逐句，可恢复 API 错误持续重试。

## 1. 目标与范围

将反馈由整篇一次 Add → Replace → Remove 改为每个源句各执行 Add → Replace → Remove，再汇总为整篇结果。每句沿用最多一轮有限返修，模型输出协议仍为本阶段操作和 handoff。

按后续要求，重建文本、对比和反馈均默认逐句调用。基线抽取、拆分、实体反馈以及反馈后的冲突处理和评估沿用原流程。text_scope 控制重建与对比，feedback_scope 控制反馈；两者可分别选择 document/sentence，以便固定上游结果单独比较反馈。主流程先汇总逐句重建，再汇总逐句对比，随后逐句执行反馈。

保留 document 与 sentence 两个反馈模式用于对照；以 sentence 为新默认，旧模式可显式选择。运行清单写入所选模式、实际执行模式和版本。第一版顺序处理句子，不引入并发。

## 2. 为什么不直接在主 pipeline 加循环

当前 karma/core/feedback_pipeline.py 的 process 每次重置 snapshots、last_revision 以及修改和问题记录。主 pipeline 调用后读取 after_add、after_replace 和 stages 并写文件。直接循环会只留下最后一次调用的状态，还可能出现相同 pass_id 的文件覆盖。

当前三元组 index 是整篇当前集合的位置；逐句执行时需改为本句当前集合的位置。源句编号 S1、S2 等保持原值，不能每句都重命名为 S1。旧差异中的 triple_indices 来自整篇拆分结果，也不能直接作为本句操作编号。

## 4. 构造每句输入

按 source_sentences 中的顺序遍历，逐句构造独立工作副本。分组依据 source_sentence_ids，不依赖三元组在列表中的排列顺序，也不重新让模型判断来源。

| 字段 | 句模式下的数据 |
| --- | --- |
| source_sentences | 仅当前源句，保留原 sentence_id |
| current_collection | 当前句的全部三元组；初始按原列表顺序编号为 0、1、2…… |
| sentence_index | 仅当前句到本句当前编号的映射 |
| comparison_bundle.source_text | 当前句原文 |
| comparison_bundle.reconstructions | 当前句重建记录，保留生成状态 |
| comparison_bundle.diff | 仅当前句 unique_to_text_a、unique_to_text_b 和状态 |
| candidate_entities | 名称或别名在当前句中能直接定位的已有候选；无匹配时 []，名单不限制可抽取对象 |
| applied_change_log | 当前句前面阶段实际发生的修改和失败摘要 |
| handoff | 只给当前句、当前阶段的问题；编号对应本句当前集合 |

差异和重建记录采用明确字段列表重新构造，避免旧记录夹带整篇原文、其他句子或原始全局 triple_indices。旧差异只作语义提示，涉及旧编号时由程序保留在审计中，不把它转换成未经核实的当前操作编号。比较数据仍标明来自本句初始 V0，后续 Replace/Remove 结合修改记录判断其是否过时。

某句三元组为空时仍执行 Add，允许发现完全遗漏的关系。差异为空也继续检查；缺少对应差异或比较失败时保留状态，不能称为没有差异。有明确 sentence_differences 时按编号取值；旧数据只有可识别的 [Sx] 前缀时按精确前缀取值，无法归句的差异留在整篇审计，不猜测分配。

## 5. 每句如何执行

1. 以本句初始三元组构建 V0。
2. Add 读取本句完整材料，输出 add、handoff；程序应用有效新增，保存本句 after_add。
3. Replace 读取 Add 后的集合、本句差异和本句修改记录；执行一条换一条或一条换多条，更新编号，保存本句 after_replace。
4. Remove 读取 Replace 后的集合，自主查重复、选择保留项，执行删除。
5. 对本句尚未成功投递到 Add/Replace 的问题，沿用最多一轮返修。返修范围仍为本句。
6. 保存本句最终结果、首次阶段快照、每次模型请求与回复、接受和拒绝的操作、问题传递记录。
7. 处理下一句。每句的版本、问题队列和修改历史互相独立。

例：S3 初始有“系统包含具有处理功能的模块”和“系统处理数据”两条。Add 判断已有表达需要修正，交给 Replace；Replace 修正第二条主语为模块、缩短第一条字段；Remove 检查修改后的两条是否重复。S2 和 S4 的三元组不参与本次操作，也不会被本句编号误删。

第一版顺序执行，因此现有 Agent 的 last_call 可在每次调用结束后立即深拷贝保存。将来并发时须为每个任务隔离这些可变状态，并处理限流，不能直接共享 Agent 对象并行调用。

## 6. 编号、汇总与输出文件

模型只使用本句当前 index。程序记录本句初始 index 到原始拆分列表 index 的映射，以及各阶段 index_map。审计定位使用“sentence_id + 本句版本 + 本句 index”；单独一个 index 不再代表整篇位置。

按源句顺序拼接各句结果，构造整篇：

- after_add：所有句子首次 Add 输出的汇总。
- after_replace：所有句子首次 Replace 输出的汇总。
- after_revision：所有句子完成 Remove 和可能返修后的最终汇总。

这些字段是各句相同处理阶段的汇总快照，不声称文章曾在某一时刻同时处于该状态。每个汇总列表另存“sentence_id、本句 index → 该快照全局 index”的映射。不能将 after_add 的编号当作 after_revision 编号。

last_revision 保留平铺 stages，便于当前耗时统计和输出代码使用；每项增加 sentence_id，并将 pass_id 写为 S3_1_add、S3_2_replace 等。每句内部问题 id 和版本留在所属句子记录中，整篇索引用句编号限定，避免同名冲突。

阶段文件示例：_dump_doc0_feedback_S3_2_replace.json。整篇 revision_result.json 保留现有主要结果字段，审计新增 scope、sentence_runs、汇总映射和异常原因。协议版本明确区分整篇与逐句。source_sentence_ids 及 evidence 均保留。

## 7. 边界与失败处理

- 每句只允许引用本句有效编号及源句 ID。引用其他句子或越界编号按现有协议失败策略处理。
- Add 部分无效仍应用其余有效操作；Replace/Remove 整批无效保留该阶段输入。某句失败不撤销其他句子结果；本句前面已经成功的修改也不被误回滚。
- 保留“已投递不代表语义已解决”，有限返修按句计数，最多一轮。
- 历史条目若关联多个源句，不能复制到多个任务后各自修改，也不能任取一个来源。第一版在任务构造前检查：存在这种共享条目或无法安全分组的记录时，该篇显式回退现有整篇反馈，记录实际模式和原因；不把回退文章计作逐句实验。正常单来源数据不触发回退。若实际数据存在此类记录，先单列统计，再决定是否追加更复杂的共享条目处理。
- 逐句 Remove 判断本句重复；汇总不自动删除跨句等价事实，也不额外调用整篇 Remove。后续既有冲突处理保持原行为。跨句重复若影响评分，单列核查，避免将新的全局去重规则混入本次实验。
- 正常 10 句约 30 次反馈调用，不含返修和底层重试；固定 Prompt 会重复发送。记录 token、耗时、失败与返修次数，用实际结果比较成本。

## 8. Prompt 与文档同步

固定文字明确当前集合是“本次输入范围内的完整集合”，源句范围由输入中的 feedback_scope 和 source_sentences 指定。逐句模式传一条源句，整篇模式传整篇源句，避免 System 中“全部”被理解为缺失了全文。

保持现有三阶段步骤、单句新事实依据、固定评分 0.8 和 9 个短示例。同步三个 Agent 的完整 MD、HTML、Prompt完整模板.json、总览与反馈分步说明。导出分别验证两个入口实际发送的 System/User；核对变量替换、固定文本、相对链接、源码行号和调用来源。

## 9. 验收与对照实验

实现验收：

1. 两句输入产生各自 Add → Replace → Remove 的六次正常调用，运行数据中没有其他句子的原文、三元组、差异或历史。
2. 保留 S3 等原源句编号；本句 index=0 与整篇 index=0 不混用。
3. 空三元组句仍执行 Add，新增只影响该句。
4. 一条换多条、转交和删除后编号映射正确，后续阶段使用实际新集合。
5. 句间异常隔离，失败回退准确；每句最多一轮返修。
6. 历史多来源条目显式回退且不复制、丢失或截断来源。
7. 三类整篇结果快照包含所有句子，审计文件名称唯一；三元组来源与阶段映射可追溯。
8. 保留整篇模式已有测试，并覆盖主 pipeline、输出文件及新配置入口。
9. 文档导出及示例协议校验通过。

效果验收：使用相同源句、after_split、重建记录、文档差异、候选实体及模型参数，对照 document 与 sentence 两种反馈范围。专用回放入口直接进入反馈，不重新运行拆分或比较。旧产物缺少某项固定输入时明确报告，不悄悄重生成替代。

统一采用用户确认的修改后 Gold，比较宽松匹配下各阶段 P/R/F1 以及反馈前后变化量；固定评估脚本和匹配参数。单列此前 doc0/S2、S3、S7，doc1/S9，doc2/S2、S3 和 doc3/S7 的问题。同时报告调用成本、失败和回退。不能用不同拆分结果的两次运行直接归因于逐句反馈；单次运行的差异也不等于稳定收益。

## 10. 实施顺序

1. 新增逐句调度模块，先完成输入过滤和编号映射。
2. 接入现有三阶段执行，汇总快照、问题记录与审计。
3. 增加配置入口、主 pipeline 输出衔接和版本记录。
4. 同步范围说明与全部受影响 Prompt 文档。
5. 完成离线测试及固定数据回放入口。
6. 用实际运行结果判断收益；如尚未运行真实模型，交付时明确这一限制。

## 11. 本次实施补充

运行代码已实现上述逐句调度、编号隔离、阶段汇总、显式整篇回退及固定输入回放。默认 text_scope 和 feedback_scope 均为 sentence。

- 重建文本 generate_sentences 每次只传一个三元组分组，原文与 evidence 仍不发送；空三元组组不调用重建模型，保留 empty_triples 状态。
- 文本对比 compare_sentences 每次只传一个源句与其重建文本。某句解析失败只标记该句，其他句子继续；API 限流不会进入这一失败回退。
- 按用户最新要求，重试仅在原 Chat Completions 机制上取消次数限制，等待逐渐增加到最多 30 秒；原数字 Retry-After 保留并封顶 30 秒。
- 原有 429、5xx、网络和超时重试条件保留；Responses 恢复原 SDK 接口处理及设置。
- 撤销额外请求间隔、抖动、408/409 重试、扩展等待头解析、分段等待和共用 api_retry 模块。当前逐句调用仍顺序执行。
- 原有非重试错误与各 Agent 失败策略保留，不增加整次运行终止规则。消息及结果记录仍用于逐句审计。
